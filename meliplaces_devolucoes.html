Autobuyer — O que é e por que importaQué es y por qué importa

O Autobuyer é o sistema que automaticamente cria o pedido de compra do device substituto assim que o retorno é confirmado. Sem ele, nenhum recambio seria completado — é o elo invisível entre a aprovação da troca e o envio do novo terminal ao cliente.

El Autobuyer es el sistema que automáticamente crea el pedido de compra del device sustituto en cuanto se confirma la devolución. Sin él, ningún recambio sería completado — es el eslabón invisible entre la aprobación del cambio y el envío del nuevo terminal al cliente.

App: mgrowth-auto-buyer Elo central do ciclo de recambioEslabón central del ciclo de recambio Sem fallback — críticoSin fallback — crítico
❓ Por Que o Autobuyer Precisa Criar uma Venda?
A infraestrutura de logística do Meli só despacha produtos que têm um pedido de compra associado
O ecossistema Meli foi construído sobre o paradigma de marketplace: para despachar qualquer produto físico, é obrigatório ter uma cadeia completa de objetos — purchase order → merchant order → shipment. Não existe atalho.

O Autobuyer foi criado justamente para navegar essa cadeia em nome do MP, permitindo despachar um device de recambio (que o cliente não paga) usando a mesma infraestrutura logística de uma venda normal.
🚫
Sem purchase order…
…não existe merchant order. Sem merchant order, não existe shipment. O endpoint de envio é POST /merchant_orders/{id}/shipments — o ID é obrigatório na URL.
📄
Razão fiscal (Brasil)
A legislação exige NF-e (ou DC-e para produtos gratuitos) para toda movimentação física de mercadoria. O ERP só emite a nota fiscal quando existe um pedido de compra registrado no sistema.
📊
Rastreabilidade
Todos os sistemas downstream (WMS, serial tracking, BigQuery, analytics) usam o pedido de compra como âncora. Sem ele, nenhum dos pipelines consegue processar o recambio.

O cliente não paga nada — o próprio MP financia internamente

Por que o preço não pode ser R$0? O autobuyer tem uma regra hard-coded: a soma dos preços dos itens deve ser maior que zero (pedido com valor zero retorna HTTP 400). O valor configurado é o custo interno do device — uma transferência financeira entre contas MP, transparente para o cliente.
⏱️ Quando o Autobuyer é Acionado no Recambio

🟡 Condicionado — Longtail (73,3% do volume)

  • Cliente solicita troca → SO + RSO criados
  • Cliente posta o device (Correios hoje / MeliPlaces amanhã)
  • Confirmação de retorno: RSO → REVERSE_COLLECTED
  • Autobuyer acionado AQUI
  • Cria a "venda" interna → gera shipment do device novo
  • Device novo enviado ao cliente
Conexão com MeliPlaces: o scan do QR na agência gera o REVERSE_COLLECTED em tempo real → Autobuyer dispara mais rápido → cliente recebe o device novo mais cedo.

🔵 Não Condicionado — SMB / Big Sellers (22,7%)

  • Cliente solicita troca → SO criada e aprovada
  • Autobuyer acionado IMEDIATAMENTE
  • Sem esperar retorno — "venda" interna criada na hora
  • Device novo enviado direto ao cliente
  • Device antigo coletado depois — mas apenas 48% são recuperados
  • Os 52% restantes que não devolvem = perda direta de hardware (device novo já foi enviado)
Fluxo não impactado pelo MeliPlaces — o autobuyer dispara imediatamente. A baixa taxa de recuperação (48%) é um problema separado de coleta ativa, não de canal de postagem.

Fluxo Fiscal — Devolução de Device sem NF Referenciada

Flujo Fiscal — Devolución de Device sin NF Referenciada

O fluxo de devolução de devices usa Declaração de Conteúdo — um documento fiscal simplificado, sem referência ao pedido original. Esta seção detalha como este documento funciona, por que é utilizado e o que muda com MeliPlaces.

El flujo de devolución de devices utiliza Declaração de Conteúdo (Declaración de Contenido) — un documento fiscal simplificado, sin referencia al pedido original. Esta sección detalla cómo funciona, por qué se utiliza y qué cambia con MeliPlaces.

📄 O Documento Atual — Declaração de Conteúdo
O Que é a Declaração de Conteúdo (DC)?
Documento obrigatório para envios pelos Correios sem natureza comercial
  • Utilizada em envios de pessoa física para pessoa jurídica (PF→PJ), sem transação comercial vigente
  • NÃO é uma Nota Fiscal — não gera créditos fiscais nem substitui NF eletrônica
  • Exigida pelos Correios para objetos postados em agências físicas
  • Sem referência à NF original de venda — o device foi vendido meses/anos antes, em transação fiscal distinta
  • Valor declarado: valor estimado do bem (geralmente custo de reposição ou valor simbólico)

❓ Por Que Não Referenciar o Pedido Original?
Justificativas técnicas e fiscais
Três razões principais para o modelo atual de Declaração de Conteúdo sem NF referenciada
📅
Tempo entre venda e devolução
O device pode ter sido comprado meses ou anos antes. A NF original pode já estar no SPED fiscal — referenciar gera complexidade contábil desnecessária.
🔧
Finalidade: manutenção, não estorno
O device retorna para reparo/reacondicionamento — não é um estorno de compra. A DC cobre remessas para manutenção sem necessidade de NF de devolução.
📦
Modelo do remetente (PF→PJ)
Sellers Longtail são majoritariamente PF (MEI). Não emitem NF de devolução — a DC é o único documento possível para este porte de remetente.

Filtro: MLB · Recambio Condicionado (Longtail) · Últimos 30 dias
SELECT
  SO.SO_ORDER_ID,
  SO.SO_CUS_CUST_ID           AS CUST_ID,
  SO.SO_LINKED_ORDER_ID       AS SHIPPING_ID,
  SO.RSO_TAG_NUMBER,
  SO.SO_ORDER_STATUS,
  SO.SO_FLOW_TYPE,
  SO.SO_DEVICE_MODEL,
  SO.SO_REQUEST_DATE,
  SO.SO_PRIORITY_CUSTOMER,
  DATE_DIFF(CURRENT_DATE, DATE(SO.SO_REQUEST_DATE), DAY) AS DIAS_DESDE_SO,
  -- Estado de origem do cliente (via pedido de compra)
  ORD.SHP_ADD_STATE_NAME      AS ESTADO_CLIENTE

FROM `meli-bi-data.WHOWNER.BT_MP_POINT_SERVICE_ORDER` SO
LEFT JOIN `meli-bi-data.SBOX_OPER_MP.TBL_LK_SDX_BASE_ORDERS_MLB` ORD
  ON SO.SO_LINKED_ORDER_ID = CAST(ORD.ORDER_NUMBER AS STRING)

WHERE
  SO.SIT_SITE_ID         = 'MLB'
  AND SO.SO_FLOW_TYPE    = 'REPAIR'
  AND SO.SO_PRIORITY_CUSTOMER = TRUE   -- Condicionado (Longtail)
  AND SO.SO_REQUEST_DATE >= DATE_SUB(CURRENT_DATE, INTERVAL 30 DAY)
  AND SO.SO_CUS_CUST_ID  != 75554443   -- Excluir outlier

ORDER BY SO.SO_REQUEST_DATE DESC
LIMIT 20
Para isolar não-postados: adicionar AND SO.RSO_TAG_NUMBER IS NULL AND SO.SO_ORDER_STATUS IN ('ORDER_CREATED','SHIPPING_CREATED')
